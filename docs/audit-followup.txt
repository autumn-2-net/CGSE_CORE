What this change fixes
----------------------
The residual selector retained only four ranked choices. Each later page rescanned
every remaining producer even when its compiler, stock and boundary were unchanged.
A single boundary with 12,000 alternatives needed 192,000 source visits to admit
64 recipes. A grant of one could also admit four, and a temporarily declined last
page could disappear because no omitted fifth choice triggered deferral.

The selector still gives each boundary a four-choice visit. It can retain up to
32 ranked choices, with at most 32 KiB of optional windows across this request.
It preserves partially consumed pages and enforces the actual admission grant.
Unadmitted candidates remain retryable. There is no increase to the 512-recipe
support limit, request work/memory limit, or the full count-closure limits.

The ranking key includes the current boundary generation. Adding a boundary
invalidates old coverage scores; recipes already admitted elsewhere are filtered
before reuse. Stock, exclusions and compiler identity are request-local. Eviction
discards optional ranking data, not pending boundaries or mathematical proofs.

Recipe admission can reclaim the windows before retrying. A declined count model
or an explicit downstream memory cutoff also reclaims them and retries the SAME
support before any further expansion. Already spent work is not refunded, and a
local handoff retains the retry. Windows and in-progress scans close with balanced
reservations; no source scoring cache survives into another inventory request.

ResidualFrontierTest compares every turn with an independent full-catalog sort,
including reordered/co-producing catalogs, eviction, exclusions, zero/one grants,
temporary admission failure, memory refusal and cancellation. ResidualNeighborhoodTest
checks exact count admission before/after reclamation and continuation of partial
scans, in addition to complete plan and force-production verification.

Remaining gaps, rather than completed checkboxes
------------------------------------------------
1. Large closures: the full count model still has 8,192-resource/recipe admission
   limits; support neighborhoods still admit only bounded supports. Residual
   expansion improves entry and reuses work but is neither exhaustive pricing
   over the full catalog nor a proof that a rejected neighborhood is impossible.
   Larger shared supports need a concrete failure family before changing limits
   or introducing another boundary representation.

2. Numeric reach: CountAffineLattice, CountKernelSearch and CountDiophantine now
   retain complete arithmetic checkpoints, including projection and verification.
   The 48-coordinate lattice admission, precision guard and natural face limits
   remain. A local numeric restriction never proves the original model impossible.
   Larger sparse equalities and subset sums still need bounded search improvements;
   see numeric-continuation-and-root-proofs.txt for the equal-budget boundary.

3. End-to-end attribution (J): seven primary graph origins have outer-validation
   outcome/work counters. RequestPlanningWork's ordinary fallback has its own
   budget/report, and not every preparation/restoration/seed phase is attributed
   to the same candidate record. Startup guards have generation/pool statistics,
   not full per-origin pruning benefit and validation-cost attribution. These are
   remaining observability gaps, not evidence of a wrong executable plan.

4. Cross-snapshot residency (H): compiler aggregation is an estimate of containers,
   not a JVM object census. It does not measure process RSS, all live networks or
   when the last host reference to an obsolete snapshot disappears. No global GC
   registry or leak claim is justified by these counters alone.

5. Integration and old limits: migration-validation.txt records the previous
   adapter/server run, not a live run of this change. Source/model oracles and
   captured-network replay do not establish AE dispatch/save/reload behavior.
   known-limits.json is explicitly an e788d3d3 observation; its old unresolved
   entries must not all be called current failures. The 2026-10-09 count-model
   replay and capacity fix are in count-corpus-followup.txt. That follow-up still
   left 32 main-count limits and six unbounded test-conversion exclusions. The
   subsequent parity-and-root-continuation.txt comparison resolves seven more
   canonical records at the same 20M budget and adds 72 parity/neighbor cases;
   It left 25 main-count limits and the same six conversion exclusions. The next
   numeric-continuation-and-root-proofs.txt boundary fixes root-proof aggregation
   and retains numeric work; its current comparison and independently checked
   remaining truths supersede that count without rewriting the old evidence.
   Historical probe assertions have not all been freshly replayed. Passing graph
   fixtures does not certify every historical integer model.

The next algorithm change should target a retained, reproducible failure in
items 1 or 2 and compare original-coordinate plans under equal resource caps.
Ordinary fallback is not assigned a cycle-solving role by this follow-up.
