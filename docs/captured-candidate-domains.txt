Captured candidate domains, 2026-10-11
=====================================

Problem
-------
CapturedRecipe.expand() and dependencies() describe the same first 256 concrete
variants. This is useful as a fast view, but is not a complete recipe domain.
For two slots with 20 candidates each, the stock-funded a19/b19 combination has
ordinal 399 and is absent from that view, as are providers reached only through
the omitted alternatives. Raising the cap cannot handle a product of many slots.

New entry point
---------------
CapturedCatalog<K> retains immutable CapturedRecipe entries, their stable IDs and
original binding IDs. Its plan()/begin() methods run the existing main graph
planner behind resumable candidate discovery. Entry order is the host's priority
order. begin() also accepts external supply, required seeds and catalyst policy.
Both synchronous and PlanningScheduler callers use the same continuation and one
cumulative PlanningBudget. Concrete GraphRecipe/GraphCompiler callers are intact.

The host must supply the complete captured provider catalog, including providers
for candidate inputs beyond the initial window. No worker reads live inventories
or pattern callbacks. A host snapshot that already discarded those providers or
alternatives cannot recover them by changing only the core jar. Mark such a
capture incomplete. Existing GTL CapturedPatternCatalog still flattens captures
before planning; adopting this entry point requires an adapter update in GTLCore.
This change does not silently change that host's capture or integration APIs.

Expansion and scope
-------------------
CapturedRecipeDomain keeps exact BigInteger cardinalities and stable mixed-radix
ordinals, without materializing the Cartesian product. Its first window has the
existing order: singles, then descending-copy mixed selections; the last slot
advances fastest. Exact composition ranking/unranking handles domains larger
than Long.MAX_VALUE. Random access does not claim that skipped ordinals exist
in the current concrete view. Emitted values and domain metadata belong to the
domain's logical reservation until close().

The first planning turn keeps the old 256-window order. A restricted turn gets
min(32768, remaining search work / 4), with a 256-work minimum; its individual
operations still charge the global budget. Failure or a bounded inconclusive
turn opens the next recovery channel, not a global missing-material conclusion.
Later contiguous pages double the covered prefix. Positive early results need
not enumerate the rest of the domain.

Potential base outputs and physical container returns are indexed without
enumerating variants. Only reachable domains are expanded. Emitting a new
variant discovers its input dependencies and their providers, including recipes
not reached by the initial window. Virtual reusable self-returns are not treated
as physical producers. Expanded domains are compiled into a new immutable
GraphCompiler; no restricted negative cache, count session, source closure or
proof is imported into a larger domain.

Result.coverage() records the request-local revision and, per reached pattern,
the covered prefix, exact total, explicitly instantiated additional ordinals,
and capture completeness. A complete relevant closure is required before a
negative result or a seed optimality certificate can escape. Otherwise the
answer is UNKNOWN (or the actual work/memory/time limit); misleading restricted
missing-material previews are removed. A verified positive witness is valid
even with incomplete coverage, but is labelled FEASIBLE_NOT_PROVEN_OPTIMAL.
An explicitly incomplete provider catalog also prevents a global negative claim.

Existing proof archives certify concrete count models, not captured domains.
Using a restricted captured view marks the archive incomplete. Individual
certificates remain independently replayable, but this archive cannot be used
as a complete full-catalog proof. CapturedProof now exports the captured domain
and concrete execution separately (see below); it does not promote those local
count certificates into full-order negative proofs. Revision numbers are local
diagnostics, not global cache identities. A changed capture must create a new
CapturedCatalog.

Factorized stock allocation
---------------------------
After the unchanged first turn fails, an optional auxiliary model finds a
stock-funded set of concrete firings. For a pattern directly producing the
requested target, it first allocates enough firings to meet the order. A failed
whole-order attempt retains the one-firing recovery for upstream or recycled
supply. It does not replace the canonical graph.
For a slot allowing mixed copies, integer variables count candidate copies and
sum to multiplier * firings. For an indivisible slot, integer variables count
whole firings selecting each candidate and sum to firings. Each physical resource has ONE upper-bound
row shared by every slot, including repeated/tag-overlapping candidates with the
same key. Exact candidate stack amounts multiply those variables. External
supply omits only the corresponding stock bound.

The existing LCG engine solves this bounded model. Its state is retained between
slices. Integral per-slot counts are swept into run-length groups; each group
restores a canonical ordinal and real GraphRecipe. The number of groups depends
on nonzero candidate counts, not the request magnitude. Mixed slots fill exactly
one slot multiplier per firing, while indivisible slots never mix candidates
within a firing. Container returns follow those exact selections.

The restored support receives one bounded main-planner turn before the full
refined catalog. This matters even after recovering all the necessary variants:
the full catalog can spend its short turn rechecking hundreds of unfunded
alternatives instead of joining two funded variants. Support trials use the
same PlanVerification and ForceCraftProof as ordinary main planning. Their
negative conclusions, caches and seed optimum claims never escape into the
full view. Failure resumes that immutable full view; later pages remain eligible.
The full view also tries sparse repairs first within their original pattern.

Only positive proposals escape this auxiliary search. Missing initial stock for
one firing does not rule out upstream production, recycling, or a combination
of several variants, so failure can try cross-pattern flow before paged discovery. Every final plan
goes through the normal original-recipe verification and shared inventory checks.
Read/configuration slots are excluded from this auxiliary model and retain the
concrete path. Likewise, a host with coupled input semantics must supply concrete
variants; CapturedRecipe's Cartesian representation assumes independent slots.

This first repair still fixes the firing count of one pattern and cannot by
itself discover allocations needing resources first produced elsewhere.
Its auxiliary search has at most 256 slots,
1024 eligible variables and min(32768, remaining search work / 8) work. Admission
refusal or a local cutoff never means infeasible. Each reached domain gets at
most one whole-order attempt and its smaller one-firing recovery; it does not
repeatedly spend work on the same failed stock view.

Cross-pattern flow and count reuse
---------------------------------
CapturedFlowAllocation adds a second positive-only view when the stock repairs
do not produce a successful plan. It reaches potential providers through ALL
eligible slot candidates, including candidates beyond the 256-prefix and
candidate-specific physical return producers. It uses one integer x per pattern
and integer u per slot/candidate: sum(u) = multiplier*x for mixed-copy slots,
sum(u) = x for indivisible slots. Base outputs multiply x; actual input amounts
and physical returns multiply u. All patterns spend and replenish the same
physical resource row, so shared raw materials cannot be independently credited
to several upstream branches. No floating-point arithmetic is used.

This is an optional restricted view, not a new canonical graph or a proof
compiler. Configuration consumption, reusable read arcs and coupled semantics
are not linearized. Admission can omit unavailable candidates and unsupported
providers; at most 512 provider patterns, 256 slots per pattern and 4096 variables
are admitted. Model construction and LCG each have a short cumulative turn,
capped at 32768 work and additionally limited by the request's remaining budget.
One request makes at most one cross-pattern attempt. Reaching a cap, a negative
row proof, or an unschedulable allocation returns to canonical discovery without
exporting any negative knowledge.

Forced-order flow proposals conservatively require net growth at least equal
to the request; explicit reserves still account for existing target stock.
This leaves productive target-seed turnover with smaller net growth to the
ordinary main solver. A net-balanced unseeded ring may satisfy the flow model;
that is a proposal, not executable production.

CapturedAllocationRecovery is shared with the stock repair. It restores the
integral slot marginals to canonical ordinals AND their exact BigInteger firing
counts in compressed groups. Counts may exceed Long.MAX_VALUE internally. The
number of restored variants depends on allocation boundaries rather than the
order size. Per-firing mixing rules and candidate-specific returns are preserved.

Keeping the counts is essential: forwarding only the support makes the main
planner repeat count search. CapturedFlowWitness passes the restored counts to
the existing CountSchedule, AllocationSearch.Candidate, PlanVerification and
ForceCraftProof. Assembly may reject an ordering and resume another ordering
of the SAME counts. Startup inventory, shared consumption, inferred/explicit
seed reserves and forced production are checked before accepting a witness.
If this short recovery fails, the support and then the full refined catalog
remain eligible for ordinary planning. Accepted witnesses, validation work and
first-verified latency enter the existing candidate metrics; construction,
search and restoration costs are attributed to allocation in the cost trace.

New upstream domains can enter coverage through sparse ordinals without first
instantiating their unrelated 256-prefix. They remain incomplete until canonical
coverage catches up. Only concrete restored variants enter the result and CGD
replay, never abstract slot-choice variables or a cross-view infeasibility claim.

Portable coverage and execution replay
--------------------------------------
After a CapturedCatalog.Work has a result (including after close()), call:

  var proof = work.certificate(20_000_000, 128L << 20);
  CapturedProof.write(Path.of("request.cgd"), proof);

The export explicitly bounds work and cumulative retained allocations. Refusal
throws CapturedProof.Limit without modifying the computed plan or its budget.
Normal planning allocates no archive. Resource identity is interned using the
original key equality, never its display string. Patterns, all captured input
alternatives, returns, request stock, external supply, required seeds, domain
coverage and the optional serial witness are included. This is a mathematical
snapshot, not a live AE key codec or a claim that the host captured every provider.

The versioned CGD1 codec bounds file size, collections, integer lengths and
decoded allocations; it rejects duplicate map keys, truncation and trailing data.
The witness is a flat backward-referencing DAG. Shared steps, deeply nested
programs and Long.MAX_VALUE repetitions never expand into individual firings.

  java -cp cgse-core-0.1.0-SNAPSHOT.jar org.cgse.core.CapturedProof request.cgd

The checker independently recomputes domain cardinalities, unpacks weak
composition ordinals, checks concrete slots/returns against the capture and
checks exact serial prefix requirements against the archived inventory. A
complete coverage claim additionally checks provider closure through every
candidate and physical return. It calls no candidate expander, graph compiler,
planner or integer solver. Public verify() reports coverage and execution
separately; no witness means execution INCOMPLETE, not UNSAT. A verified witness
certifies delivery and explicit seed goals, not automatic seed optimality.

Proof limits remain explicit. Orders that consume target seeds and have positive
net gain below the requested amount require the planner's stronger turnover
minimality proof; the independent execution checker returns INCOMPLETE for that
case. CGD1 does not serialize that extra proof, whole-order infeasibility, or
assumption-transfer links from arbitrary earlier CGP count journals. Restricted
count archives consequently retain their existing incomplete marker.

Validation
----------
CapturedRecipeTest keeps the legacy expansion/dependency order and exact budget
checks. A >256-candidate mixed slot previously built more singles than its capped
selection count and threw; the first-window path now stops singles at that count.
Saturated products use long intermediates instead of overflowing int arithmetic.

CapturedRecipeDomainTest compares 90 prefix configurations, exact full weak
compositions from an independent vector enumerator, and rank/unrank round trips.
It checks huge domains, empty inputs, capture truncation, arithmetic overflow,
cancellation and reservation cleanup.

CapturedInputAllocationTest compares 600 factorized assignments with independent
exhaustive slot assignments, including overlapping resources, unequal stack
sizes, physical returns, indivisible slots, mixed copies and external supply.
Its 12 slots x 300 alternatives case has 531441000000000000000000000000 possible
combinations. The funded last combination is found after only 257 instantiations
(the initial 256 plus one sparse repair), with 47601 total work and about 1.79 MiB
peak logical reservation in the local JDK 17 run.

CapturedCatalogTest reproduces the missing 400th combination, later dependency
providers and later return producers. It covers joint supply across several
variants, sparse ordinals later absorbed by full coverage, shared stock across
patterns, Long.MAX_VALUE orders, 120 candidate/catalog order permutations,
stock replenishment, changed captures, forced production, incomplete proof
archives, budget limits, cancellation and one/four-worker scheduling.

Initial domain implementation validation: all 87 standard programs/batches pass, including the
20M/80M pinned count boundaries. All 244 curated graph fixtures pass in three
orders (732 cases). Offline Gradle assembly passes; all 209 production sources
in the source jar match the validated working-tree files. Final production
fingerprint: d6616fc352fb8b4fff1ffb5c32e8f87e0f711a8d879aeccde241719a2554ace4.

Final local artifacts stay under build/candidate-focused-final-20261011 and
build/candidate-fixtures-20261011; build/candidate-final-20261011 is the initial
standard pass before the final ownership refinement. Player captures and temporary reports are not
part of the production change. These are core regressions, not a new live-server
integration test of the unchanged AE adapter.

Batch recovery and replay follow-up
----------------------------------
The split-stock counterexample has 12 slots x 300 alternatives, with 1000 units
of each slot's last TWO candidates and an order for 2000 outputs. At identical
200k search / 200k compilation caps and 64 MiB logical memory, ded8a215 returns
SEARCH_LIMIT after 337465 combined work and 17082773 peak logical bytes. Recovering
two variants without a support trial still exhausts the allowance. With the
multi-firing allocation and positive-only support trial, it returns a verified
FEASIBLE_NOT_PROVEN_OPTIMAL after 59218 combined work and 2171433 peak logical
bytes, instantiating 258 of 531441000000000000000000000000 combinations. These are
work/reservation comparisons, not a claim about stable wall-clock speedup.

CapturedBatchAllocationTest includes 600 independent exhaustive multi-firing
comparisons, shared resources, mixed/indivisible slots, external supply and
24 wide-domain candidate permutations under one/four-worker scheduling and
optional expanded budgets. It checks Long.MAX_VALUE aggregate counts, memory
refusal and cancellation. Every wide result also passes independent CGD replay.
CapturedCatalogTest retains the sparse-to-contiguous absorption case using a
variant needing upstream production, so the new stock recovery cannot mask it.
CapturedProofTest checks independent weak-composition enumeration, archived
coverage and witness tampering, display-name collisions, returns, required seeds,
unfunded prefixes, 10000-deep programs, shared DAGs, file bounds and replay limits.

Follow-up validation: all 89 standard programs/batches and all 732 fixed
fixture/order cases pass on JDK 17. Offline Gradle assembly passes. The 211
production files in the source jar match the tested tree, with fingerprint
0f4c8b272d88a72a755cfce6f468c4b6d868da79c36f93c046420e4849cfeb19.
Local results are in build/captured-batch-20261011 and
build/captured-batch-fixtures-20261011. This remains a standalone-core change;
the GTL adapter has not adopted CapturedCatalog or CGD export in this boundary.

Cross-pattern validation boundary
---------------------------------
The upstream counterexample keeps the 12 slots x 300 candidates and order 2000,
but replaces each stocked last candidate with a raw material and a 1:1 upstream
provider. Each slot has two independently stocked raw materials of 1000 units.
At the same 200k search / 200k compilation caps and 64 MiB logical memory,
865e0732 returns SEARCH_LIMIT: 339634 combined work, 18371607 peak logical bytes,
and 4096 main-domain variants expanded. Cross-pattern allocation plus count reuse
returns FEASIBLE_NOT_PROVEN_OPTIMAL: 56486 combined work and 1880053 peak logical
bytes. It instantiates 256 prefix variants, two recovered main variants and
24 upstream variants. These are deterministic work/reservation measurements,
not a wall-clock speedup claim.

CapturedFlowAllocationTest adds 600 independent acyclic exhaustive comparisons:
enumerate concrete downstream firings, ceil the exact upstream deficits, and
compare all upstream consumption against common raw stocks. Every positive flow
is restored, scheduled and checked against the actual stock. Another 24 wide
candidate/provider permutations cover one/four-worker scheduling and expanded
budgets, with independent CGD replay. Long.MAX_VALUE upstream orders, aggregate
counts above long, physical returns, explicit reserves, forced existing-target
stock, external supply, startup-dead rings, stock replenishment, optional memory
refusal and cancellation are covered. The prior sparse-prefix absorption test
now uses a declined dispatch-input provider so that it continues to exercise
canonical paging instead of being bypassed by the new successful flow view.

Dispatch-group optimization remains outside this view. In particular the old
configuration-input boundary with 300 alternatives, only a299 produced from
one consumed configuration raw, and an order of two outputs can still exhaust
20M work on both 865e0732 and this version. dispatchInputs(2) consumes one raw
per provider call, but a Batch can be split across calls: the current serial
verifier reserves two raws and rejects a one-raw witness. The regression checks
that distinction; it is NOT a verified feasible-order counterexample. Supporting
that optimization would require a stronger dispatch contract as well as recovery,
not simply relaxing the stock row. The per-firing flow model declines it.
Likewise this change does not provide whole-order negative CGD certificates or
connect the GTL adapter to the captured-domain entry point.

Validation: all 90 standard programs/batches and all 732 fixed fixture/order

files in the source jar match the validated tree; production fingerprint:
