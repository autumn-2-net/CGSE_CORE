New reproduced F2 gap: lost uses without lost eligibility
--------------------------------------------------------
Take one blue tool with n uses and one specialized red tool with n+1 uses.
Warm both unchanged, spend n general uses to produce parts, then spend n red-only
uses to turn those parts into products. The general rule can use either color.
All ordinary inputs are present. A literal witness uses blue for the first stage
and red for the second, retaining the red tool with one use at completion.

Before this change, longer-lived-tool ordering spends some red capacity in the
general stage. The resulting red states still satisfy the specialized rule at
each such transition, so eligibility-loss feedback never starts. Subsequent
failure asks for additional entities even though another assignment of the same
owned tools, counts and execution word succeeds. The public captured entry on
dc635259 returns UNKNOWN for n=3,7,31; this is a search gap, not a false global
UNSAT proof or attribution to a specific player report.

Choice recovery now also admits an observed cross-rule reduction in guaranteed
uses. It first preserves the existing eligibility-loss ordering, then prefers
transitions which do not reduce protected rules' positive capacity. The feedback
does not simulate unused durability states, exclude any eligible edge, reserve
tools, change counts or learn a mathematical cut. Every candidate still needs
original source restoration, exact funding/production checks and verification.
The existing eight-rule/512-score cache and 32768/one-sixteenth lifetime allowance
remain unchanged. In a945e37f, the broader execution-order scout still retained
its old eligibility-only admission; the next increment addresses that boundary.

The four original n=2,3,7,31 requests now all solve. The old n=2 positive keeps
exact search/compilation work and peak reservation. Current public search work
for n=3,7,31 is 24933,25680,30282, with 3739 compilation work each; the old failures
used 27260,27578,29570 search work. A newly solved request need not use less work
than an earlier incomplete failure. These are work counters, not speedup claims.
CapturedStateCapacityChoiceTest retains 77 positive variants plus negative and

Follow-up F2 gap: same tools, different temporal order
----------------------------------------------------
One tool starts with n+2 uses. A light rule removes one use, while a heavy rule
requires at least two and returns the tool with one use. The order needs n light
parts and one heavy part. Light n times followed by heavy once is a constructive
witness. Heavy first leaves the tool eligible for light, but unable to complete
the remaining n uses. There is no second initial tool key to choose instead.

On a945e37f, requesting heavyPart before lightPart in the finishing recipe and
listing [heavy, light, finish] gives UNKNOWN for n=2,3,7,31,127. Reversing the source
list recovers those same requests through another count proposal. This ordering
dependence is a local recovery gap, not missing material or a global UNSAT proof.
The original lightPart-first inputs also solve; both orders are retained locally.

Execution-order admission now consumes the same witnessed guaranteed-use loss as
entity-choice recovery. The existing scheduler promotes the blocked variant and
replays identical counts from original stock. All ordinary gates, exact state
transitions, entity ownership and final checks remain mandatory. This extends
only admission and its diagnostic reason; the eight-word limit, lifetime work
allowance and existing fallback/refinement paths stay unchanged.

The five old UNKNOWN cases now solve. At n=7, public search work changes from
1801 (UNKNOWN) to 1019 (feasible); the already-positive reversed-source case goes
from 1671 to 1017. The n=1 controls keep identical work and peak reservations.
Retaining an order continuation can add temporary memory to an old positive:
at n=31 in reverse order, peak reservation grows from 97328 to 106420 bytes while
search work falls from 2898 to 2244. These are counters, not wall-time promises.
CapturedStateCapacityOrderTest retains 69 positive combinations plus blocked
ordinary gates, insufficient raw material, work caps and cancellation controls.
Local original inputs, source orders, hashes and runs are registered under

Validation of this ordering increment: all 69 combinations pass with independent

Follow-up F2 gap: incompatible repeated promotions
-------------------------------------------------
With several destructive rules on one physical tool, moving only the newly
blocked variant to the front can undo a previously useful order. A constructive
family starts at tool:n+levels+1: light uses subtract one, while heavy rule k
requires at least k+1 and returns tool:k. Light n times, then heavy levels..1,
then ordinary finishing is executable. On 8ef89118, 76 of 96 source/slot-order
variants solve; 20 remain UNKNOWN despite that literal witness.

Recording every local failure as a permanent order preference was insufficient:
damage accumulated earlier can make a later harmless use appear responsible,
creating contradictory hints. The retained approach instead compares one-step
effects on the proposal's selected activation keys after repeated plain failures.
It builds a bounded preference graph over selected variants and tries one stable
topological rank. Cycles do not establish a deadlock; they leave the plain order.
Ordinary dependencies can override a rank, and exact restoration remains required.

The analysis is capped at 64 variants and min(4096, one quarter of the order
continuation's remaining work), with a 256-work minimum. Simple three-rule cases
get a third ordinary attempt before analysis; longer interactions start after
two failures. Only one structural word can be added. Its rejection restores the
interrupted plain candidate, retaining all eight ordinary attempts inside the
same original 32768/one-sixteenth lifetime allowance. This is a scheduling hint,
not a learned precedence, an expanded state domain or a global negative proof.

All 96 variants now solve. Among the original 76 positives, search work decreases
on 32 and is identical on 44. Peak reservations decrease on 20, stay identical on
52 and increase on four because of the small hint workspace. At levels=8,n=31,
order=0, public search work falls from 15492 to 5983, compilation work from 2208
to 1919, and peak reservation from 299820 to 182395 bytes. These are recorded
counters; no universal timing or complete temporal-assignment claim is implied.

The maintained integration test covers 109 positive combinations plus negative
gates/material and limit controls. The hint unit test independently checks 60
acyclic graphs and 212 physical words, fallback preservation, cyclic hints and
64/65-variant/memory/cancellation boundaries. Nineteen existing state, allocator,
scheduler and runtime programs pass against the frozen baseline and final code,
with identical reported output. Local original inputs, failed approaches, source
hashes and commands are kept under state-order-feedback-20261018. This is focused
validation, not a full corpus or live-host run.
Assemble, integrated Forge/AE-dump packaging and all 1478 baseline ABI entries
pass. Both new tests also pass against the packaged engine; only
CapturedStatePlanning and StateScheduleRepair differ among 753 engine classes.

Still open, with concrete implementation boundaries
---------------------------------------------------
1. F1: Arbitrary unique one-way states still require explicit selected transitions.
   StateFamily has one-step algebra only. General symbolic/after-many operations
   would also need execution, verification and persistence contracts. Observed
   repetition is not a complete symbolic-state solver.
2. F2: General temporal entity assignment remains incomplete. Feedback changes
   preferences and bounded proposals; it is not an exhaustive search over every
   entity choice, tool-manufacturing history or execution order. Repeated failure
   of the same protected rule does not renew the optional allowance.
3. Sections 5.2/5.3 and 8A: RecipeCountModel still relaxes per-push configuration
   consumption. Stable provider batch bounds are not a captured global contract.
   CapturedRecipeDomain remains Cartesian; correlated legal tuples must still
   arrive as concrete valid variants. A table/MDD relation API and restoration
   support are not implemented by this patch.
4. Sections 6/7/8D/E: Coverage revisions and CountModelViews semantics/mappings
   exist. Changed captured coverage starts a fresh compiler, preventing stale
   restricted proofs from escaping. CountRowTemplates verifies original material
   derivations against current rows. General incremental semantic metadata,
   proof reinstantiation across added columns, transformed symmetry metadata,
   and pricing over ungenerated symbolic candidate domains remain open. Existing
   finite-matrix ExactColumnProgram is not that domain oracle.
5. Sections 5.4/8B/C/F: Nominal execution plus actual return/replan is not a robust
   AND/OR policy for every random outcome. General integer cut-conflict chains,
   native relation/domain-hole explanations and state automata are research
   extensions. Existing PB/MIR/LCG tools do not establish their completion, and
   the review did not establish that every extension is required for this engine.
6. Section 10: Whole-request candidate lineage, source-preparation/host-install
   attribution, and process-wide retained heap/RSS remain separate from the
   existing work-account and pipeline metrics.

Next improvements should target measured restoration or captured-domain failures.
For related-slot tables, first preserve actual legal tuples through every
allocation/recovery/proof path; an independent-marginal flag alone is unsafe.
No new public API, host adapter, version bump or solver budget is needed for
the guaranteed-use feedback corrections above.
