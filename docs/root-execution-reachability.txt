Root execution reachability, 2026-10-11
=====================================

Baseline: 7c54a97e (close solver gaps exposed by full regression).

Problem and change
------------------
The integer count equation can have many solutions while every execution needs
more simultaneous startup material than the request owns. Pebbling cases expose
this gap: tools/working slots are returned eventually, but cannot be shared by
simultaneous prerequisites. Excluding one unschedulable count vector at a time
can spend the whole 20M request allowance without settling the order.

After a concrete scheduling failure and 32K count-search work, the main count
search can try the existing forward execution engine against its original root
recipes, stock and goals. This is one bounded request-local attempt, admitted
only with no incumbent, at most 32 keys and 64 recipes, and no consumed per-push
configuration inputs. Exact reusable read arcs are supported. Optional compiled
program searches do not recursively start it.

Full-transition traversal complements the existing persistent-set traversal.
A reduced traversal may find a witness without visiting a boundary closed under
all original transitions; that visited set alone cannot prove absence. The new
mode explores every enabled transition, then uses the independent ExecutionProof
checker to verify the entire visited boundary against all original recipe arcs.
No marked exit is allowed in this root certificate. The existing seed search
keeps its persistent-set mode and independently checked proof boundary.

Safety and accounting
---------------------
The search ignores incidental count-branch bounds and decision clauses. External
supply is projected away and the inventory goal relaxes forced-production and
implicit seed-preservation requirements. Therefore failure of this weaker
problem proves the actual scoped order impossible. Its proof never becomes an
empty count-model conflict: an execution impossibility need not contradict the
state equation. Restricted neighborhood callers continue to consume witnesses
only; their negative results do not escape to the full recipe catalog.

A positive execution trace goes through the ordinary candidate assembly and
original-recipe verification, including forced production and seed preservation.
Even an empty trace covering stock cannot bypass these checks. Program-to-count
conversion retains its continuation and charges repeated call edges. The root
proof remains local to this inventory/request; it is not cached as a conclusion
for a later order. Opt-in archives serialize its full execution certificate.

Search is allotted min(32768, remaining order work / 32, current count turn's
remaining allowance). Candidate validation gets a separate allocation of
min(131072, remaining order work / 32). Bounded steps can cross a local scheduling
allocation; all their work is charged to the same global order cap. The independent
closure check includes work already spent in the current step when calculating
its remaining allowance. Search cutoffs,
memory refusal and incomplete proof checks leave the primary count frontier
available; they never become an infeasibility result. Scratch and frontier bytes
are reserved, and completion, refusal and cancellation release ownership.

the baseline implementation makes its root regression exhaust 20M; the current
implementation completes it with an independently checked execution proof.

Limits
------
This is bounded explicit state search, not a complete general Petri-net decision
procedure. Large or growing state spaces can still return UNKNOWN. Large sparse
integer equalities need other tools; widening CountJump's pair search was tested
separately and rejected after reducing solved cases at equal work. No such pair
search change is included here.
