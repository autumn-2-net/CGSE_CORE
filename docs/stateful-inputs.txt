Stateful inputs and physical returns
===================================

StateFamily<K> describes captured algebra for a tool, charge container or other
consumable state. Attach it to CapturedRecipe.Candidate.family and retain the
CapturedCatalog when using RequestPlanningWork.capturedCatalog(...). Supplying
only the legacy concrete prefix cannot recover the omitted states.

Capture and identity
--------------------
StateFamily implementations must be immutable and safe to call on a planning
worker. They must not read a live world, inventory or mutable host object, or
invoke live recipe callbacks. An immutable key codec may reconstruct captured
identities through frozen registries. Keys need stable equality and hash codes.

id() identifies the complete rule, including per-use cost and invariant state
semantics. Equal IDs must mean interchangeable algebra; different costs or
incompatible rules need different IDs. accepts(key) must check the invariant
data, not just the item's basic type. capacity(key) is a nonnegative guaranteed
number of complete uses from ONE physical entity, not expected random lifetime.
nominalAfterOne(key) supplies one legal exact return, or null for consumption.
Its successor must preserve the remaining guarantee. Unchanged states and
saturated Long.MAX_VALUE lower bounds are supported; neither implies expansion
of the whole possible lifetime.

StateReturn<K> separately describes the complete finite outcomes of one exact
input state. exact/consumed describe deterministic returns; alternatives carries
explicit possible outcomes and a completeness flag. An empty outcome means no
remainder. A sampled callback or expected-value approximation is not a complete
contract. requireExact() rejects incomplete or stochastic contracts; hosts must
explicitly supply the runtime outcome protocol for uncertain returns.

Capacity proposals and exact restoration
----------------------------------------
CapturedStatePlanning is an internal positive-only auxiliary view. Activation
spends a physical entity and supplies family-use capacity. Different worn tools
retain their own capacities; an entity cannot be activated twice. Ordinary
producer recipes can manufacture further tools. Capacity keys exist only in the
auxiliary coordinates, never in host inventory or a submitted physical plan.

The restorer allocates actual entities to every slot before releasing that
operation's returns. It generates only selected exact states and restores real
GraphRecipe/PlanStep values, then checks funding, execution and the request.
Aggregate capacity alone cannot prove that enough separate tools exist for a
multi-tool operation or that fragments can be combined. Dispatch still needs
the physical inputs: use capacity does not permit concurrent reuse of one tool.
For slots whose supported candidates all use the same family, the auxiliary
model also requires the simultaneous entity count as a read arc. Activation
supplies one entity marker as well as use capacity. This lets the proposal select
additional stocked or manufactured tools instead of repeatedly relying on one
long-lived entity. Markers are not physical inventory and do not prove that the
entities survive every later use. Slots with different family/ordinary choices
do not acquire unconditional requirements from independent choice marginals.
The arc is only added for simultaneous demand above one: positive use capacity
already requires an activation, so ordinary one-tool recipes keep the smaller view.

Simultaneous slots of one family are allocated jointly against the actual owned
state keys. A retained search assigns indivisible slots to whole same-key groups,
trying best-fit first and backtracking when that choice blocks another slot.
Mixed slots then use the remaining entities, preferring longer-lived states.
No returns become available until every slot of the firing has been allocated.
The single-family, single-tool path does not build this allocator. Allocation failure concerns
these exact owned entities and slots, not all possible programs or count vectors.

When several rules accept the same physical state, one activation offers their
marginal capacities and restoration uses a shared owned-entity pool. Those
capacities are not independent lifetime guarantees: every selected use applies
its own exact transition to the same physical entity. A returned state remains
owned if any captured rule can still use it, including when the just-used rule
has exhausted its own capacity. A total entity read arc for fixed simultaneous
choices prevents one activation from funding several concurrent tool slots.

Slots with different eligibility rules use joint integral matching. Whole-key
indivisible demands branch over state keys; mixed and unit demands use retained
capacitated augmenting paths. A failed flow backtracks the whole-key assignment,
rather than rejecting a valid alternative. Counts are never expanded into one
node per entity. Failure is local to this firing and physical inventory.

If a failed allocation needs an activation already selected by the proposal,
restoration may advance that activation only when its physical input is currently
owned. Ordinary inputs of the current firing are reserved first. A per-binding
credit skips the corresponding later activation, so an entity is never activated
twice. This can use a manufactured replacement as soon as it is present; it cannot
borrow a future manufacturing output. Shared-rule slots may reassign eligible
owned entities; different rules never create another copy of the physical tool.

If entities are still insufficient, a local repair can re-propose with each
activation's capacity capped by the selected number of firings using that family.
One physical tool can serve at most once per firing. This prevents a long-lived
tool from substituting for several concurrent short-lived tools in that candidate,
and can request extra stocked or manufactured replacements. The firing horizon is
only a proposal restriction, not a bound on every valid execution of the catalog.
All old restored inventory, activation credits and coordinate-local plans are
discarded before solving the changed auxiliary model. The allocation DFS retains
its frontier between steps; a changed capacity model starts a new auxiliary solve.
If marginal capacities overlook combined wear, a further positive-only proposal
can require one more activated entity eligible for the failed rule. That floor
is a candidate restriction, not a necessary bound on the original problem. It
may request production of a replacement; actual restoration still cannot use
that replacement until it has been produced and physically claimed.
Neither path renews the arm's original work allowance or borrows cache-preparation
budget. General temporal matching and a complete restoration repair procedure
are not implied by these bounded positive searches. In particular, arbitrary
transitions that first become eligible for an unrelated rule are not a complete
state-domain expansion, and an auxiliary decline is still inconclusive.

Exact transitions are interned within the same auxiliary variant, retaining the
source binding, family choices, input slots and full outputs. Repeated execution
words can therefore share recipe IDs. An immutable transition returning the
identical state admits a serial Repeat without enumerating each firing: exact
ordinary-resource prefix bounds limit the repeat count. Consumed configuration
inputs remain charged per iteration; the runtime still gates each provider push
on actual owned inputs and received returns. No shortcut is assumed for arbitrary
changing-state callbacks. A periodic state word may be compressed after its exact
selected transitions have been restored, using the existing plan optimizer.

Physical state seed requirements are checked on the restored final state. They
are omitted from the capacity proposal, where activation consumes the physical
key without representing its final return. This relaxation cannot authorize
losing a required seed: assembly and final verification retain the original seeds.

Restoration consumes work and memory budget and has cancellation checkpoints;
very large requested executions may still exhaust that budget.
Restoration, assembly and verification have separate cost-trace stages. Candidate
diagnostics include restored firings, unique transitions, program nodes, restore
calls and work. Internal outcomes distinguish verified candidates, restricted
declines and local resource limits, including invalid algebra versus insufficient
entities. Diagnostics also count candidate horizon refinements and advanced owned
activations. The arm cannot continue beyond its original fixed allowance.

A failed auxiliary solve or failed restoration is not a global negative proof.
Family domains remain incomplete; a verified witness is
FEASIBLE_NOT_PROVEN_OPTIMAL, while restricted failure cannot become INFEASIBLE.
Other captured paths may continue. The existing finite-domain CapturedProof
export rejects family catalogs because it cannot serialize this algebra.
General custom dynamic outputs, arbitrary world-dependent transitions and
unbounded stochastic outcome protocols are not supported by this interface.

Runtime return ownership
------------------------
GraphJobRuntime.Adapter.returnChoices supplies OutputObligations.ReturnChoice
for guaranteed finite alternatives: input slot, predicted output key, allowed
keys and the physical quantity owed by that dispatch. Every key represents the
same owed quantity; alternatives are not additional inventory. The predicted
quantity must already exist in the recipe's execution outputs. Exact returns
continue to use ordinary output obligations.

Disjoint domains and equivalent contracts (same predicted key and allowed set)
can run concurrently. Equivalent owners share FIFO receipts, including partial
receipts across saved flights. Non-equivalent overlapping domains wait for older
owners to settle; incompatible overlaps within one batch are rejected before
push. Fixed outputs or external supply cannot overlap an active choice domain.
Aggregate return headroom is reserved before inputs leave the runtime.

A nullable nominal return is not a mandatory ReturnChoice. If the sound nominal
plan consumes the tool and the complete outcome contract also permits survival,
the host may route that unpromised bonus to ordinary storage. It must not promise
a surviving tool or leave a mandatory wait for the empty outcome. Generic
optional/multi-output contracts cannot be passed as single-key choices.

An actual alternative retires the predicted obligation and credits only the
received key. A changed state freezes the old suffix. beginReplan and inventory
forecasting wait for all variable-return owners to settle; stateReplanReady then
permits a checkpoint and a validated replacement suffix. Persistence must retain
remaining choices and needsStateReplan. A save during provider handoff preserves
ambiguous ownership and cannot authorize automatic redispatch or input refund.
Cancellation refunds only held inventory; late machine returns go to the host's
ordinary storage. Host adapters must publish and clear all alternative-key
subscriptions, including synchronous returns and rejected dispatches.

Regression entry points
------------------------
The public tests are under tests/core/java/org/cgse/core:
  StateTransitionTest: exact/unknown contracts and finite closure boundaries.
  CapturedStateTest: large state spaces, separate worn entities, new tools,
    configuration inputs, unchanged/saturated capacity and proof/budget limits.
  CapturedStateRestoreTest: fixed points up to one billion firings, repeated
    state words, entity read arcs, manufactured tools, slot/order alternatives,
    exact seed preservation, per-dispatch inputs, cost attribution and actual
    return gating through save/load of a production-restored plan.
  StateEntityAllocationTest: 28,002 independent tiny allocation oracle cases,
    indivisible backtracking, large counts, retained depth and cancellation.
  CapturedStateEntityTest: changing stock/slot order, mixed and indivisible
    multi-tool firings, attrition, replacement production and activation ordering,
    physical source-level replay, saved runtime returns and restricted limits.
  StateEntityMatchingTest: 56,798 independent finite allocation cases with
    different slot eligibility, whole-key/flow rollback, wide counts and limits.
  CapturedStateSharingTest: sequential cross-rule reuse, simultaneous matching,
    combined wear and replacement production, disjoint rules, physical seeds,
    primitive replay, delayed returns/save-load, request coverage and work caps.
  CapturedReachableTest: sparse candidate recovery and exact execution checks.
  RequestCoverageTest: request-level coverage and restricted-result boundaries.
  StateReturnRuntimeTest: alternatives, equivalent parallel owners, persistence,
    rejection, cancellation and checkpoint/replacement behavior.
  StateReturnConcurrencyTest: aggregate headroom and transient subscriptions.
  StateReturnPlaceholderTest: completion markers cannot discard pending returns.

These are core regressions. A host must additionally test actual provider
capture, dispatch, inventory routing and persistence in its own environment.
