Stateful inputs and physical returns
===================================

StateFamily<K> describes captured algebra for a tool, charge container or other
consumable state. Attach it to CapturedRecipe.Candidate.family and retain the
CapturedCatalog when using RequestPlanningWork.capturedCatalog(...). Supplying
only the legacy concrete prefix cannot recover the omitted states.

Capture and identity
--------------------
StateFamily implementations must be immutable and safe to call on a planning
worker. They must not read a live world, inventory or mutable host object, or
invoke live recipe callbacks. An immutable key codec may reconstruct captured
identities through frozen registries. Keys need stable equality and hash codes.

id() identifies the complete rule, including per-use cost and invariant state
semantics. Equal IDs must mean interchangeable algebra; different costs or
incompatible rules need different IDs. accepts(key) must check the invariant
data, not just the item's basic type. capacity(key) is a nonnegative guaranteed
number of complete uses from ONE physical entity, not expected random lifetime.
nominalAfterOne(key) supplies one legal exact return, or null for consumption.
Its successor must preserve the remaining guarantee. Unchanged states and
saturated Long.MAX_VALUE lower bounds are supported; neither implies expansion
of the whole possible lifetime.

StateReturn<K> separately describes the complete finite outcomes of one exact
input state. exact/consumed describe deterministic returns; alternatives carries
explicit possible outcomes and a completeness flag. An empty outcome means no
remainder. A sampled callback or expected-value approximation is not a complete
contract. requireExact() rejects incomplete or stochastic contracts; hosts must
explicitly supply the runtime outcome protocol for uncertain returns.

Capacity proposals and exact restoration
----------------------------------------
CapturedStatePlanning is an internal positive-only auxiliary view. Activation
spends a physical entity and supplies family-use capacity. Different worn tools
retain their own capacities; an entity cannot be activated twice. Ordinary
producer recipes can manufacture further tools. Capacity keys exist only in the
auxiliary coordinates, never in host inventory or a submitted physical plan.

Initial discovery of stocked keys, external supply, source outputs, candidate
keys/returns and family identities is retained between steps. It does not scan
the whole capture in the constructor. Every step checks cancellation, time and
the arm's original work allowance, and reserves key/family storage before
insertion. Large discovery may decline locally, leaving the canonical captured
path its remaining budget. This is neither a negative state theorem nor a new
allowance on resumption. It does not unfold unused nominal tool states.

The restorer allocates actual entities to every slot before releasing that
operation's returns. It generates only selected exact states and restores real
GraphRecipe/PlanStep values, then checks funding, execution and the request.
Aggregate capacity alone cannot prove that enough separate tools exist for a
multi-tool operation or that fragments can be combined. Dispatch still needs
the physical inputs: use capacity does not permit concurrent reuse of one tool.
For slots whose supported candidates all use the same family, the auxiliary
model also requires the simultaneous entity count as a read arc. Activation
supplies one entity marker as well as use capacity. This lets the proposal select
additional stocked or manufactured tools instead of repeatedly relying on one
long-lived entity. Markers are not physical inventory and do not prove that the
entities survive every later use. Slots with different family/ordinary choices
do not acquire unconditional requirements from independent choice marginals.
The arc is only added for simultaneous demand above one: positive use capacity
already requires an activation, so ordinary one-tool recipes keep the smaller view.

Simultaneous slots of one family are allocated jointly against the actual owned
state keys. A retained search assigns indivisible slots to whole same-key groups,
trying best-fit first and backtracking when that choice blocks another slot.
Mixed slots then use the remaining entities, preferring longer-lived states.
No returns become available until every slot of the firing has been allocated.
The single-family, single-tool path does not build this allocator. Allocation failure concerns
these exact owned entities and slots, not all possible programs or count vectors.

When several rules accept the same physical state, one activation offers their
marginal capacities and restoration uses a shared owned-entity pool. Those
capacities are not independent lifetime guarantees: every selected use applies
its own exact transition to the same physical entity. A returned state remains
owned if any captured rule can still use it, including when the just-used rule
has exhausted its own capacity. A total entity read arc for fixed simultaneous
choices prevents one activation from funding several concurrent tool slots.

Slots with different eligibility rules use joint integral matching. Whole-key
indivisible demands branch over state keys; mixed and unit demands use retained
capacitated augmenting paths. A failed flow backtracks the whole-key assignment,
rather than rejecting a valid alternative. Counts are never expanded into one
node per entity. Failure is local to this firing and physical inventory.

If a failed allocation needs an activation already selected by the proposal,
restoration may advance that activation only when its physical input is currently
owned. Ordinary inputs of the current firing are reserved first. A per-binding
credit skips the corresponding later activation, so an entity is never activated
twice. This can use a manufactured replacement as soon as it is present; it cannot
borrow a future manufacturing output. Shared-rule slots may reassign eligible
owned entities; different rules never create another copy of the physical tool.

When several distinct initial keys were activated and a witnessed transition
disabled a later rule or reduced its guaranteed uses, restoration can first retry
the same counts AND execution word with different entity choices. A still-eligible
state may no longer fund all later uses. Failure admission checks the witnessed
cross-rule transition's entity totals first, then its quantity-weighted guaranteed
capacity using exact integers. These observations do not prove a necessary bound.
Failed rules guide a preference for exact transitions that retain eligibility,
then preserve guaranteed uses among otherwise equally ranked choices. The original
eligibility priorities dominate every capacity tie-break. Single-rule allocation orders supplies
and its best-fit alternatives; multi-rule matching orders each slot's allowed
edges. Every supply and eligible edge remains searchable. These preferences
neither reserve tools nor prove that a tool must be saved for a later operation.
Whole-key backtracking and residual augmentations still decide one-firing
feasibility; the ordering is not a minimum-cost or complete temporal allocation.

This optional feedback retains up to eight distinct failed rules and 512 cached
rule/state scores within one unchanged proposal. Its lifetime allowance is at
most 32768 work units and one sixteenth of remaining request work, including
subsequent restoration. Admission requires 16384 remaining work, at most 128
active variants and 2048 ports. Preferences apply to at most 256 owned eligible
keys and, for joint matching, 32 simultaneous demands. No domain is truncated:
larger allocations use the ordinary allocator. If the extra preference workspace
does not fit, allocation retries without scores before declining for memory.
Repeated failure of the same rule
does not restart this scout. A changed proposal clears all feedback and scores;
the enclosing arm's fixed allowance still covers every attempt. Order recovery
and entity refinement remain available if the chosen physical assignment fails.

If the same protected rule fails again, selected activation states can admit one
additional quantitative choice trial. Two choices must share the existing
eligibility/wear score yet differ in the blocked rule's exact one-step capacity
loss. The analysis admits at most eight families and 256 sampled states, uses at
most 1024 work and one eighth of the choice scout's remaining lifetime, and needs
at least 64 work. It neither enumerates unobserved states nor supplies an entity.

That trial breaks equal qualitative scores by nonnegative lost uses, compared as
long values without narrowing, floating point or summed weights. Eligibility and
qualitative wear retain their original priority. Both whole-key allocation and
cross-rule matching precompute immutable costs before sorting. Optional cost
workspace yields to the existing qualitative allocator when it cannot fit.
There is only one cost trial per unchanged proposal, within the original lifetime
allowance, including downstream restoration. A failed trial clears its cost bias
before ordinary choice/order recovery continues. It is a positive heuristic for
one repeatedly blocked rule, not a minimum-cost matching or temporal proof.

Per-edge ranks do not minimize a whole firing's assignment cost. A breadth-first
augmenting path can consume a protected free tool while a longer alternating path
would preserve it. During the existing qualitative/quantitative recovery, bounded
joint optimization can improve that feasible allocation before its tools are used.
It admits at least two slots and keys, at most 32 slots, 256 keys and 1024 candidate
edges. If every slot is indivisible and has the same amount q, optimization uses
one integral cohort per slot and floor(stock/q) cohorts per key. Physical stock
remainders stay untouched: the cohort view never combines different keys to fund
one slot. Unequal whole-slot sizes or a mixture of whole and split slots retain
their original allocator. Existing ranking and result scans also record whether
every chosen edge achieves its slot's exact
minimum price. A flow meeting that lower bound skips optimization without more
score callbacks, edge visits or restoration retries.

The optimizer uses bounded negative-cycle cancellation, as in the existing
count-network optimizer, directly on the owned allocation residuals. A reservoir
accounts for unused supply. Each checked cycle changes all of its edges atomically
and preserves every slot total and physical supply. Exact integer prices minimize
total qualitative penalty before total one-step wear; the latter is retained when
the earlier quantitative trial was admitted. Quantities never expand into entities.
Whole-cohort prices use the original demand amounts; removing the common factor
q preserves both objective priorities. Atomic cycle updates also change the
original whole-slot choices and physical unused counts by q times the cohort
exchange. Their extra workspace and normalization work share the same allowance.
At most eight cycles and min(4096, remaining request work / 32) work are available
per matching, including score callbacks. Memory/work refusal keeps the existing
feasible flow. This is not a global temporal optimum or a negative proof.

It does not add another whole-word trial. Its work remains inside the existing
choice recovery, covered by the original 32768/one-sixteenth lifetime and the
enclosing arm's allowance; it never renews or borrows cache budget. Ordinary
choice/order recovery and the existing quantitative-bias cleanup remain intact.

An auxiliary proposal can omit a useful initial tool key even when more stock
exists. After ordinary choice feedback fails, one isolated stock-support replay
may add funded surplus tools. It subtracts all selected activations and gross
ordinary inputs from captured initial stock before claiming any surplus. It never
creates stock from a declared state, an external supply or a possible producer.
The original source counts and execution word remain fixed; exact assembly and
verification still enforce actual input funding, final seeds and force crafting.

The replay owns separate physical pools, choices and verification state while
retaining the parent's failed prefix and matching explanation. Failure resumes
that original continuation. Choice feedback is copied with its original lifetime,
including previously witnessed quantitative wear preferences. New failures may
adjust the isolated choices; one bounded secondary pass also considers observed
cross-rule resource loss, below existing failed-rule edge priorities. This can
avoid spending a tool through one slot when another slot will need it later.

Admission allows at most 128 activation keys, 128 sources/selected recipes,
32 families and 2048 selected input ports. Surplus discovery has at most 2048
work or one eighth of remaining choice work. The replay receives at most half
the remaining choice/arm allowance, capped at 16384; speculative restoration
stops at 8192, while an assembled physical word can finish verification within
that reserved share. Secondary feedback is capped at 1024 or one eighth of
remaining choice work. No allowance is renewed and cache budgets are unchanged.
If initial-stock recovery fails, one separate count proposal may request a
manufacturable tool cohort omitted by the current support. Declared ordinary
outputs identify possible tool keys; the minimum simultaneous/lifetime cohort
for a used rule supplies a positive search hint. It does not supply inventory.
Old source/activation counts remain lower bounds, while the count solver must
fund additional manufacturing through actual captured recipes and stock.

This private proposal adds a read coordinate from the requested activation to
selected consumers of its rules. It prevents the auxiliary scheduler from
placing a multi-step manufacturing chain after the consumers that need it.
The coordinate has no physical counterpart, does not enter the canonical graph,
and is removed by exact source restoration. Original material funding, source
slots/outputs, simultaneous tool ownership, final seeds and force crafting are
verified again before publishing any plan. A failed trial retains the original
failed prefix and matching explanation, then resumes ordinary order/count work.

Manufacturing support is admitted for at most 128 auxiliary entries, 128 selected
counts, 128 seed keys, 32 families and 2048 ports. Its entire discovery/count/
restoration/verification trial gets at most half the remaining choice/arm work,
capped at 16384. Discovery gets one eighth of that share, capped at 2048; count
repair gets at most half the remainder. Exact restoration keeps its existing
8192 speculative cap and may finish assembly within the same total share.
The original choice lifetime is not renewed, and this trial runs at most once
per outer continuation. It explores one proposed cohort, not every possible
manufacturing history; failures never establish global infeasibility.

When an already restored transition disables another rule's physical eligibility
or reduces its guaranteed uses, the restorer can retain the proposal's exact
counts and try other execution words before requesting more entities. A single
tool may need its light uses before a heavier operation even when that operation
leaves the tool eligible for one more light use. Entity-choice recovery cannot
repair this one-key case. The blocked variant guides a bounded preferred
scan: newly enabled rules are reconsidered after activation or production. Later
failures can promote another blocked variant while retaining earlier ordering
hints. The ordinary count scheduler remains a separate resumable continuation.
These hints never impose a necessary precedence or exclude a count vector.
Each attempt starts again from actual initial stock and empty activation credits;
no partial physical inventory survives. Every candidate still undergoes exact
entity allocation, source restoration, seed/production checks and verification.
An unavailable ordinary input or rejected final assembly may resume order search.

This optional repair admits at most 128 active variants and 2048 input/output
ports. It tests at most eight ordinary candidate words within a lifetime allowance capped
at 32768 work units and one sixteenth of remaining request work, including failed
downstream restoration. It neither renews the enclosing arm nor spends cache
preparation budget. On allocation failure, memory refusal or exhausted alternatives
retain the existing entity-refinement path. Scheduler failure is inconclusive for state families.
Admission first checks witnessed cross-rule eligibility loss, then remaining-use
loss with exact quantity-weighted arithmetic. Both are ordering hints only;
ordinary material gates still constrain every candidate word. This is not
complete temporal matching or state-domain exploration.

Repeated multi-rule failures can also request one structural ordering attempt.
After two plain candidates fail (three for a three-rule family), it compares
one-step effects on exact keys of the proposal's selected activations. Those keys
can be stocked or manufactured; this analysis never makes them available early.
A rule that reduces another rule's eligibility or guaranteed uses suggests
trying the latter first. Only selected variants enter the preference graph;
no unused trajectory is unfolded and no precedence becomes a necessary cut.

This pass admits at most 64 active variants and consumes at most 4096 work units
and one quarter of the order scout's remaining lifetime, with a 256-unit minimum.
The graph and ranking workspace are reserved before allocation. A stable
topological rank preserves the ordinary promotion order among unconstrained
variants. Cyclic hints are ignored, retaining the plain order; even acyclic ranks
must obey all ordinary material gates and exact physical restoration.
At most one extra structural word is tried inside the same original lifetime
allowance. Its rejection restores the interrupted plain preferred word, so it
does not remove one of the eight ordinary attempts. Exhaustion still leaves
entity refinement/canonical recovery inconclusive; no budget is renewed.

If entities are still insufficient, a local repair can re-propose with each
activation's capacity capped by the selected number of firings using that family.
One physical tool can serve at most once per firing. This prevents a long-lived
tool from substituting for several concurrent short-lived tools in that candidate,
and can request extra stocked or manufactured replacements. The firing horizon is
only a proposal restriction, not a bound on every valid execution of the catalog.
All old restored inventory, activation credits and coordinate-local plans are
discarded before solving the changed auxiliary model. The allocation DFS retains
its frontier between steps; a changed capacity model starts a new auxiliary solve.
If marginal capacities overlook combined wear, a further positive-only proposal
can require one more activated entity eligible for the failed rule. That floor
is a candidate restriction, not a necessary bound on the original problem. It
may request production of a replacement; actual restoration still cannot use
that replacement until it has been produced and physically claimed.
Neither path renews the arm's original work allowance or borrows cache-preparation
budget. General temporal matching and a complete restoration repair procedure
are not implied by these bounded positive searches.

After a capacity proposal fails, CapturedStateExpansion can expose a small
exact cross-rule boundary to the ordinary graph compiler. It starts from initial,
declared and ordinary-produced keys, retaining keys eligible for a supported
state rule. Exact returns are followed only when they gain eligibility for a rule
that could not use the predecessor. This can recover a tool cycling between
otherwise disconnected rule domains without unfolding every durability or charge
value. Changes that only lose eligibility do not launch another finite solve.
This helper admits at most 128 sources, 32 rules, 128 eligible states and 4096
input/output/candidate ports, including newly added candidates. Unsupported
state inputs retain only their original finite captures.

Original input modes, multiplicities, source bindings and physical outputs are
retained. Derived candidates freeze the immutable rule's exact nominal return;
their successor must respect its remaining guaranteed capacity. Discovered keys
never become inventory. A fresh private catalog owns new variant identities and
incomplete coverage; it imports neither canonical negative facts nor a previous
finite view's proof scope. Its first short attempt uses existing physically funded
forward recovery, then the usual graph/count portfolio. The parent hands off
half of its actual remaining lifetime allowance, capped at 262144 work units;
admission requires at least 1024 units in that handoff. It reuses the ordered
eligible keys already discovered by activation instead of testing every ordinary
inventory key a second time. Initial, declared and manufactured eligible states
remain candidates, never manufactured stock.

The forward attempt starts with at most 8192 units and one sixteenth of the
boundary allowance. Once, it can continue to at most half the boundary's remaining
starting allowance (still capped at 8192) when observed net target progress
predicts affordable completion, or assembly/verification has already begun.
This scheduling estimate is charged, has no proof meaning, and cannot renew
either the boundary or parent lifetime budget. The remainder stays available
for count recovery and validation. Exact verification, physical seeds and forced-production checks precede
acceptance; a private miss, workspace refusal or quota exit resumes the original
incomplete capture without an infeasibility claim. This is bounded positive
recovery, not a complete state closure or arbitrary symbolic-state solver.

For catalogs larger than 128 sources, CapturedStateSupport first attempts a
request-local selection for this positive state arm. It borrows the existing
captured producer index, starts from the target and exact required seeds, and
retains all captured candidates and providers of each discovered input. For each
supported state rule, it also checks indexed producer keys for positive usable
capacity. This includes manufactured non-prototype tools and sources connected
only by a captured actual return. It neither unfolds nominal transitions nor
copies unrelated source domains. Entry identity, priority, bindings and physical
stock remain unchanged; the 128-source expansion limit applies to this selected
support rather than the entire unrelated catalog.

The selection is retained across steps and admits at most 128 sources, 4096
ports, 32 rules and 8192 requested keys. It requires 16384 remaining work and
uses at most 65536 compilation work units or one sixteenth of remaining work.
Selection and the selected/full state attempts share the original state arm's
single lifetime allowance. A selected miss resumes the full original state
attempt with the remaining allowance; a declined selection starts that original
attempt directly. The ordinary canonical path remains available afterwards.
There is no transfer of negative facts or completeness from the selected view.
Finite captured producer discovery is not a complete oracle for arbitrary
opaque state callbacks, and a missing provider cannot prove global infeasibility.

Repeated requests can borrow a completed source selection from the same immutable
capture under the bounded structural-hint cache described in
captured-candidate-domains.txt. Target and required-seed keys define this scope;
all physical stock, capacities, proposals and returned states are request-local.
The private auxiliary capture suppresses optional refill previews its owner cannot
use. Complete ordinary captures retain their existing refill behavior.

CapturedStateReuseTest exercises 48 cold/warm budget/order combinations with
512 or 16384 unrelated sources, sparse/full inventory and different initial tool
states. Its known feasible low-budget boundaries require source-level physical
replay; larger stock scans may still return UNKNOWN under very small quotas.
There is no general stock-key eligibility cache: immutable family callbacks must
still inspect a new request's previously unseen inventory. This remains a limit
when a very large inventory is paired with a small compilation/state allowance.

Exact transitions are interned within the same auxiliary variant, retaining the
source binding, family choices, input slots and full outputs. Repeated execution
words can therefore share recipe IDs. An immutable transition returning the
identical state admits a serial Repeat without enumerating each firing: exact
ordinary-resource prefix bounds limit the repeat count. Consumed configuration
inputs remain charged per iteration; the runtime still gates each provider push
on actual owned inputs and received returns. No shortcut is assumed for arbitrary
changing-state callbacks. A periodic state word may be compressed after its exact
selected transitions have been restored, using the existing plan optimizer.

Within one unchanged auxiliary variant, repeated exact transitions can also
trigger an observed-cycle checkpoint during restoration. A word is reusable
only when all activated tool pools return to the same keys, multiplicities and
iteration order. Its ordinary-input prefix requirements and resource deltas
bound the number of complete copies; consumed configurations remain charged
per firing. The restored program retains a serial Repeat of those exact
transitions. Every runtime push still waits for actual physical inputs.
Tool activation, entity loss, changed variants and proposal refinements discard
the checkpoint. Manufacturing replacement tools cannot masquerade as a closed
orbit. A word may accelerate successive long-sized cursor windows of an exact
larger count. Optional checkpoint memory is released on decline or completion;
work, cancellation and the arm's original allowance remain in force.
This reuses observed finite words, without assuming that arbitrary state rules
are periodic or that unobserved states may be skipped. Distinct one-way state
chains do not allocate a checkpoint for every transition. An observed orbit is
an executable witness, not a completeness proof for the family domain.

Restoration also observes heterogeneous Repeat boundaries already present in the
auxiliary program. The boundary identifies a live cursor occurrence, including
its position and remaining iterations; sharing the same program node does not
authorize skipping another occurrence or a partially executed body. After an
exact transition has recurred, the restorer can retain a word spanning several
source recipes and several iterations. It repeats that word only when all ordered
tool pools recur and ordinary prefix requirements permit every copy. Counts of
physical firings remain exact even when their sum exceeds long.
Nested ordinary batches, serial fixed-point dispatches and separately verified
inner state cycles compose into the same prefix/delta summary. Consumed
configurations are charged per serial dispatch. Source identities remain in the
word; activation (including previously advanced activation credits), tool loss
and proposal changes invalidate the checkpoint. Declined workspace admission
keeps the existing restoration path and never increases the arm allowance.
This consumes an explicit auxiliary loop, not a proof that an arbitrary flat
schedule has a repeat or that every physical ordering has been explored. A
capacity proposal that cannot yet be scheduled remains a separate search limit.

The count scheduler can now construct such loops when a fixed recipe scan splits
one return cycle across multiple passes. It retains a bounded word of already
executed passes and combines their exact prefix requirements and deltas. Extra
copies must fit both current resources and the remaining count of every recipe;
an activation or exhausted branch cannot silently recur. This is a candidate
acceleration, with no new negative inference. If accelerated scheduling fails or
assembly rejects its witness, the same scan is retried without the shortcut.
Word construction uses the current scheduling allowance, preserves continuation
state between visits, and releases its optional workspace before assembly.
It does not change the physical state proof: the restored tools must still recur
at an exact auxiliary loop boundary before restoration can skip any firings.

Physical state seed requirements are checked on the restored final state. They
are omitted from the capacity proposal, where activation consumes the physical
key without representing its final return. This relaxation cannot authorize
losing a required seed: assembly and final verification retain the original seeds.

Restoration consumes work and memory budget and has cancellation checkpoints;
very large requested executions may still exhaust that budget.
Restoration, assembly and verification have separate cost-trace stages. Candidate
diagnostics include restored firings, unique transitions, program nodes, restore
calls and work. Internal outcomes distinguish verified candidates, restricted
declines and local resource limits, including invalid algebra versus insufficient
entities. Diagnostics also count candidate horizon refinements and advanced owned
activations. The arm cannot continue beyond its original fixed allowance.
Cycle diagnostics include the number of jumps and exact firings represented by
their retained words; prefix analysis and checkpoint matching belong to restore
cost, not a fresh search allowance.
The analogous loop_jumps/loop_firings counters identify reuse at heterogeneous
auxiliary Repeat boundaries, separately from single-variant cycle jumps.
retry_same_counts and order_candidates identify state-feedback order attempts;
their scheduling cost remains separate from physical restoration and verification.

A failed auxiliary solve or failed restoration is not a global negative proof.
Family domains remain incomplete; a verified witness is
FEASIBLE_NOT_PROVEN_OPTIMAL, while restricted failure cannot become INFEASIBLE.
Other captured paths may continue. The existing finite-domain CapturedProof
export rejects family catalogs because it cannot serialize this algebra.
General custom dynamic outputs, arbitrary world-dependent transitions and
unbounded stochastic outcome protocols are not supported by this interface.

Runtime return ownership
------------------------
GraphJobRuntime.Adapter.returnChoices supplies OutputObligations.ReturnChoice
for guaranteed finite alternatives: input slot, predicted output key, allowed
keys and the physical quantity owed by that dispatch. Every key represents the
same owed quantity; alternatives are not additional inventory. The predicted
quantity must already exist in the recipe's execution outputs. Exact returns
continue to use ordinary output obligations.

Disjoint domains and equivalent contracts (same predicted key and allowed set)
can run concurrently. Equivalent owners share FIFO receipts, including partial
receipts across saved flights. Non-equivalent overlapping domains wait for older
owners to settle; incompatible overlaps within one batch are rejected before
push. Fixed outputs or external supply cannot overlap an active choice domain.
Aggregate return headroom is reserved before inputs leave the runtime.

A nullable nominal return is not a mandatory ReturnChoice. If the sound nominal
plan consumes the tool and the complete outcome contract also permits survival,
the host may route that unpromised bonus to ordinary storage. It must not promise
a surviving tool or leave a mandatory wait for the empty outcome. Generic
optional/multi-output contracts cannot be passed as single-key choices.

An actual alternative retires the predicted obligation and credits only the
received key. A changed state freezes the old suffix. beginReplan and inventory
forecasting wait for all variable-return owners to settle; stateReplanReady then
permits a checkpoint and a validated replacement suffix. Persistence must retain
remaining choices and needsStateReplan. A save during provider handoff preserves
ambiguous ownership and cannot authorize automatic redispatch or input refund.
Cancellation refunds only held inventory; late machine returns go to the host's
ordinary storage. Host adapters must publish and clear all alternative-key
subscriptions, including synchronous returns and rejected dispatches.

For DAG execution, each resource subscribes only unfinished operations that do
not already have a notification in the awakened queue. A receipt removes a
notified operation from all its input subscriptions until that operation is
polled again. Resubscription precedes provider handoff so synchronous receipts
remain visible. Completion removes subscriptions; reload builds them only for
the unaccepted suffix. Resource-local ranks preserve the original recipe order,
including after retries, while the existing two ready lanes retain fairness.
Small subscriber sets use one scalar word; larger sets use hierarchical bitmaps
and reverse input incidences. Storage is linear in retained input incidences,
and repeated callbacks do not scan already-notified or completed consumers.
This also applies to distinct source bindings that cannot share a transition ID.
Notifications do not confer material ownership: actual held inputs still gate
every dispatch, and every owed return must arrive before completion.

Regression entry points
------------------------
The public tests are under tests/core/java/org/cgse/core:
  StateTransitionTest: exact/unknown contracts and finite closure boundaries.
  CapturedStateTest: large state spaces, separate worn entities, new tools,
    configuration inputs, unchanged/saturated capacity and proof/budget limits.
  CapturedStateRestoreTest: fixed points up to one billion firings, repeated
    state words, entity read arcs, manufactured tools, slot/order alternatives,
    exact seed preservation, per-dispatch inputs, cost attribution and actual
    return gating through save/load of a production-restored plan.
  StateEntityAllocationTest: 28,002 independent tiny allocation oracle cases,
    indivisible backtracking, large counts, retained depth and cancellation.
  CapturedStateEntityTest: changing stock/slot order, mixed and indivisible
    multi-tool firings, attrition, replacement production and activation ordering,
    physical source-level replay, saved runtime returns and restricted limits.
  StateEntityMatchingTest: 56,798 independent finite allocation cases with
    different slot eligibility, whole-key/flow rollback, wide counts and limits.
  CapturedStateSharingTest: sequential cross-rule reuse, simultaneous matching,
    combined wear and replacement production, disjoint rules, physical seeds,
    primitive replay, delayed returns/save-load, request coverage and work caps.
  CapturedStateOrderTest: two/three/five interacting state rules, recipe/slot/stock
    permutations, simultaneous entities, long-sized quantities, manufactured
    replacements, impossible ordinary gates, exact seeds and force/preserve modes.
    Source-level replay, delayed runtime returns/save-load, cancellation and
    incomplete family coverage remain mandatory after order repair.
  StateScheduleRepairTest: 250 independently constructed executable multisets,
    physical-prefix replay of alternative words, exact counts above long,
    lifetime downstream-work limits, missing stock and memory/cancellation cleanup.
  CapturedStateChoiceTest: forced material order with one/two/three specialized
    tools, several distinct physical keys, mixed/indivisible and cross-rule slots,
    long-sized requests, exact seeds, repeated conflicting feedback and limits.
    Every source transition and count is checked; small plans get primitive
    replay and delayed runtime returns/save-load. Private failure is inconclusive.
  CapturedStateCapacityChoiceTest: delayed exhaustion while an earlier cross-rule
    use leaves the specialized tool eligible; literal blue-use/red-finish witnesses,
    source/slot/stock permutations, simultaneous mixed/indivisible tools and wide
    physical cohorts. Exact seeds, forced production, delayed returns/save-load,

  CapturedStateCapacityOrderTest: one-key tool cohorts require light uses before
    a heavier transition which still leaves the light rule eligible. Source/slot/

  StateOrderHintsTest: 60 independent acyclic preference graphs, cyclic/backward

  CapturedStateChoiceCostsTest: 85 positive cases with unequal cross-rule wear,

  StateChoiceCostsTest: 1501 exhaustive-oracle allocation comparisons with exact
